Factory

You bring the idea and the judgment. Agents bring the work.

about 2h15 no programming required live install and exercise

2 min

This is a job change, not a tool change. Nobody here writes code today.

You learn to run a line that builds software. You decide, you check, you ship. Agents do the typing.

By the end, you can take an idea you already have and put it live.

The shift

You do not write the code any more.
You run the line.

Old way

  • One person, one language, one file at a time.
  • The knowledge lives in one head.
  • Speed depends on typing.

This way

  • You say what you want. Agents build it. Machines check it.
  • The knowledge lives in the repository.
  • Speed depends on how clear you are.

Typing was never the slow part.
Deciding what done means is.

4 min

Ask who has waited for the one person who knew how the system worked. That person is the bottleneck we are replacing.

A factory is a good picture. Stations with a clear output, and an inspector between the line and the customer. Here, agents run most of the stations.

Agents do not get tired. They also do not notice when the thing they are building is wrong. That stays your job.

Before the factory

Twenty minutes, once

You do not configure anything. The agent runs the setup. You answer questions and say yes.

What you do

  1. Get the code. Clone the repo, or download the zip. Any folder will do.
  2. Say one sentence: "clone the repo and set up the software factory."
  3. Answer three questions: a vault or not, where it lives, which file your agent reads first.
  4. It checks the install from another folder. Then it hands over.

github.com/FSS-IoT/software-factory-vault

What it installs

  • The vault, if you want one.
  • The factory, inside it or on its own.
  • One line in your agent's instructions.
  • Nothing else. No packages, no accounts, no service.

Do not skip the check. Open a new session in a folder with no project, and ask where the vault is.

Without it, every session starts from zero.

Changes get written without a spec, a check, or a way to ship.

15 min, live

Install first, explain later. Attention is highest here, and they leave with something running.

Do it with the room. Show the repo URL, clone it, then read the three modes from the setup skill: new vault, existing vault, standalone. That is the only decision they make.

When the skill asks about a vault, stop and take the next slide. That is the question they will have.

Finish with the check. A new session, a folder with no project, and one question: where is the vault? If it cannot answer, fix it now. Everyone else's will fail the same way.

Before the factory

The vault is the agent's memory

One folder of markdown. Your agent reads it when a session starts, and writes to it as it learns.

Vault/
├── AGENTS.md          read this first
├── Home.md            the index
├── projects/          one page per project
├── user/              how you like to work
├── system/            this machine
└── software-factory/  the method
  • One page owns each fact. Other pages link to it.
  • Agents write without being asked. You correct them, and the correction stays.
  • Two preference files: how the work runs, and how you like to work.
  • Want a vault on one topic? Those pages become the database for the next project on it.

You do not manage it. You read it, and you correct it. If an agent needs to be told to save something, the setup is wrong.

5 min

Start with the problem. A session starts with no memory. It does not know your machine, your taste, or last week's decision.

A chat history is not memory. Nobody reads it, and the agent cannot search it next month.

The fix is dull and effective: a folder, one page per subject, one index, and a contract that says where facts go.

Point at the two preference files. The factory's own is how the work runs. The user one is tone, tools, what they are learning.

The research case is worth a sentence. Point an agent at a subject, let it read and write for a week, and the vault becomes the database the next project starts from.

Say the last line plainly. They should never have to say "remember this".

The line

Four stations, one loop

The strip is the plan: your words, research if you need facts, the interview, the signed spec. The four boxes are the loop, and they run on every milestone.

5 min

Start with the strip. Nobody writes a brief document. The brief is the sentence you said out loud. Research is the quiet step when the idea needs facts first. The interview turns both into decisions. You sign the spec.

None of that is a station. It happens once, and it produces the plan every milestone answers to.

Then the loop. Four stations, and every milestone runs all four. The return arrow lands on tickets, because milestone two uses the same brief and spec.

The loop can run with an agent alone. You are needed at the plan and at the review, not at the keyboard.

Before the loopThe brief

It starts with a sentence

Your first words are the brief. That is usually all it is: one sentence, in your own words.

  • What it does: one sentence, in plain words.
  • Who uses it: what device, what room.
  • What it must do: the rules that are not negotiable.
  • What it works with: systems, budget, deadline, policy.
  • Taste: two things you like, two you hate. Name them.

A file is optional. Write it down if the idea is big. Otherwise say it, and let the interview pull the rest out of you.

WHAT YOU TYPE

I want to build <one sentence>.

Here is everything I know:
- who uses it:
- where they use it:
- it must:
- it must never:
- it has to work with:
- done means:
- I hate when software:

Do not build anything yet.
Read this, then interview me
until you can write the spec.

6 min

The brief is not a document and not a station. It is the sentence that starts the project. Nobody has to write anything before they talk to the agent.

Try it with the room. Ask for an idea and say it out loud, badly. The mess is the lesson. It does not have to be well said, it has to be said.

Facts beat adjectives, even in one sentence. "Loads in under a second on the office wifi" is a fact. "Fast and modern" is a wish, and the interview will come back for it.

If the idea needs reading first, say so here. Research is allowed to take a day.

Before the loopThe interview

It interviews you, hard

The agent hunts for the vague parts while they are still cheap to fix.

  • Nothing gets built while the questions are open.
  • Every answer lands in the spec, or in "out of scope".
  • Vague answers get pushed until you can test them.
  • "I don't know" is an answer. Let the agent decide and explain why.
  • It may argue. That is the job.
  • Run it again on a milestone with no tickets yet.
  • You end it. Stop when the answers stop changing.

10 min

Hard does not mean rude. It attacks the idea, not the person. Expect a wall of questions, and answer in shorthand. The agent does the writing.

Demo it if you can. Take the brief from the last slide and ask for the interview. Let the room watch twenty questions go past, then point at the two that found something you had not thought about.

Watch for the agent that starts building anyway. The last line of the brief stops it.

The vault calls this step grill. Same thing, plainer word.

Nobody here needs technical answers. "Should it email me or show a badge?" is a question about their own job, and it is what this step produces.

Before the loopThe spec

A spec is a contract you can test

One page. If it needs more, the idea is not settled. Go back to the interview.

It contains

  • The promise: what it does, in the user's words.
  • Behaviours: numbered, and each one checkable.
  • Out of scope: what it will not do.
  • Open questions, each with a name.
  • The whole project. Milestones are slices of it.

One behaviour looks like this

3. Given a signed-in user,
   when they enter the wrong password,
   then the screen says
   "That password is wrong"
   and the field is cleared.

# a person can check it
# a machine can check it too

Wrong at the spec: a conversation.
Wrong after the build: the build.

6 min

This is the hinge. Everything after it is mechanical. It is the last place where a decision is cheap.

Read the spec out loud. Circle any sentence that cannot become a yes or no check. That circle is the next interview question.

Out of scope is not a rejection. It is a promise you keep, and writing it down ends the argument in week three.

The spec lives in the repo as SPEC.md, next to the code. It is versioned like everything else.

Station 01Tickets

One ticket, one check

Cut the spec into slices. Each slice must finish, and you must be able to check it.

Too big, never finishes

"Build the login system."

No end, no check. Weeks of work, nothing to hand over.

Right size, finishes today

"A wrong password shows an error and clears the field."

One behaviour, one check, one closed ticket.

  • If you cannot write the check, the ticket is too vague, not too small.
  • Slice by behaviour, not by layer of the system.
  • Foundations first: the thing that stores data before the thing that shows it.
  • A design ticket is real work. A session that ends in a document is a deliverable.

7 min

Use the service desk picture. This room already thinks in tickets. An incident has a symptom, an owner and a close condition. Same shape.

One test for a good ticket: could somebody who missed this meeting pick it up and know when it is finished? If not, cut it smaller.

One ticket is one checkable behaviour. It does not have to be one commit; red and green are two, and the red one is the proof.

In a real project of mine, three features each got a ticket that was only "run the design session". Each closed with a document instead of code, and that was right.

Station 02Red / green

Write the check before the code

The check fails first. A test that never failed proves nothing.

  • Red proves the check can fail. Without it, green means nothing.
  • Green proves the change did what the ticket asked.
  • Two commits: the failing check, then the code.
  • The red commit is allowed to be red. It stays off main.
  • The agent runs the loop. You read the result.

8 min

The picture that lands is a checklist. The agent may not tick a box it has not first seen fail. Otherwise done is an opinion.

This is what protects you from confident nonsense. An agent can write a check that always passes. Red first catches it.

Do not teach them to write tests. Teach them to ask for proof: show me the check failing before you fix it. That sentence is worth the whole station.

Two commits, not one. The red commit is the proof, and a reviewer can open it and run it. If that check turns out to be fake, the ticket goes back and the pair is rebuilt from the commit before red. Keep the code, throw away the checks.

Station 03Review

The agent's work is a proposal

Done is a claim. A reviewer who was not there is the test.

Ask these four

  • What did it change, in plain language?
  • What did it leave out that the ticket asked for?
  • Open the red commit. Does the check fail there?
  • What did this break that used to work?

Then a second agent reads it

  • A fresh agent sees the change with no memory of writing it.
  • It hunts for gaps, not style.
  • The reviewer decides. You can overrule.

Approval closes the ticket. The commit goes on it, and the milestone keeps going until the last one.

Break it on purpose. Change a number, invert a condition, delete a term. Run the checks. If they stay green, the behaviour was never tested and the ticket goes back.

6 min

You can review without reading code. Read the summary, the ticket and the evidence. Then ask what was left out. That question finds most of the problems.

Ask for the red commit and run the check there. If it passes, the check was fake, and the ticket goes back. The pair gets rebuilt, and the code is kept.

The second agent is not ceremony. The author is kind to its own work. A fresh one is not.

Then break it on purpose. Change a bound, invert a condition, delete a term. Run the whole suite. If every check still passes, the checks around that behaviour are decoration. One or two mutations, then revert; this is a probe, not a campaign.

If the project has CI, CI does the mechanical checks. This station is still the judgment, and CI cannot do that part.

Station 04Ship

Ship closes the milestone

A milestone is done when its objectives are complete and the thing is live. Shipping is the closing move. The default is one per milestone.

When the last ticket is closed

  • Every ticket in the milestone is closed, with its commit.
  • Merge the work to the branch that is real.
  • Deploy the way this project deploys. One path, every time.
  • Open it and prove it is live. The build machine is not a user.
  • Close the milestone with the commit range.

What the project page records

  • Where the code lives, and which branch is real.
  • How it deploys, in one line.
  • How you know it is live.

Ship every ticket if you like. Some projects deploy on each ticket. That is a preference you can set in your own copy. The method only asks that something ships.

5 min

Keep the two apart. Review closes the ticket. Ship closes the milestone.

Complete does not mean perfect. It means everything agreed for this stage is done, and someone can use it.

Why not ship every ticket? You can, and a live service with real users probably should. For a class project, the end of a milestone is a natural moment to show someone.

Say your own habit as a preference. You ship every time, because you would rather see it early. The seed ships per milestone because it is easier to teach.

For a project with no server, push and say plainly that it is not deployed. Do not let them call a push a release.

The logbook

Git is the factory's memory

You will not type git commands. The agent does. You need the words, because every conversation uses them.

commitA snapshot of everything, with a note saying why it changed.
branchA copy of the project for one change, so main keeps working.
pull request"Here is my change, please check it." A conversation with a diff attached.
mergeThe change joins main. From here it is everyone's problem.
historyEvery snapshot, who made it, when, and why. Nobody has to remember.

The rule that matters: commit small, and make the message say why. "Fix bug" is worthless in six months. "Reject the wrong password, because the field kept the old value" is a paragraph of memory.

8 min

Do not open a terminal. Use the diagram. If they remember one thing, it is that main is what is live, and a branch is somewhere safe to try.

Commit messages are the cheapest habit here, and the one they can enforce from day one: make the message say why.

Reassure them. Agents run the commands, and mistakes are recoverable. Git keeps every snapshot, including the bad ones.

The plan

Milestones are the plan.
Issues are the work.

  • Issue: a numbered ticket with the ask, the conversation and the close condition.
  • Milestone: a group of issues that ship together, like a release.
  • Labels: bug, spec, blocked. Cheap, and they end arguments.
  • Chat is not a plan. If it is not an issue, nobody is tracking it.

7 min

This is where the factory becomes visible to management. The board is the line's state. The milestone is the shipment date.

A real one from this term: eleven issues, foundation first, then the visible features, then the documentation. All eleven closed and deployed.

Enforce the close condition. An issue closes with a commit, not with a feeling. Otherwise the board lies within a week.

Optional machinery

A robot checks every change

CI builds the project on a fresh machine and runs every check. Every time.

Optional, and a topic of its own. Bring it in once the loop works. It can run beside the loop, or take over the mechanical half of review: does it build, do the checks pass, did anything else break. It cannot tell you the thing is worth building.

  • CI runs on every push and every pull request, not on your laptop.
  • Green means you may merge. Red means blocked.
  • CD takes green main and deploys it, the same way every time.
  • It replaces "it worked on my machine" with evidence.

8 min

Say the quiet part first. This is optional, and it is the broadest topic in the deck. Runners, secrets, environments, caching. Nobody needs it to run the loop in this room.

Where it fits: beside the loop, or in place of the mechanical half of review. It never replaces the judgment about whether the thing should exist.

Ask how often something worked for them and then failed for the person next to them. That gap is what CI closes.

Two rules if they adopt it. Nothing merges red, and the deploy path is the same every time.

One habit worth taking: a red build is the highest priority ticket in the building.

The floor

The repository remembers the project

The repo holds the decisions, the checks and the code. The vault holds what a repo cannot: which projects exist, and how each one ships.

project/
├── BRIEF.md        what you asked for
├── SPEC.md         what it will do
├── docs/adr/      why decisions were made
├── README.md      how to run it
├── .github/       the robot's instructions
├── tests/         the checks
└── src/           the code
issues + milestones live in the tracker, not here
  • A decision with no reason gets argued again every month.
  • The next agent reads it cold, with no memory of your meeting.
  • Code without its brief, spec and checks is a folder of files.
  • Your vault sits outside the repo, and remembers you across projects.

Write for the next agent. It is a new colleague every morning: fast, literal, and ignorant of everything you said out loud.

5 min

This habit decides whether the workflow survives a real week. Everything else can be improvised. This cannot.

Name the ADR folder. Architecture decision record sounds grand. It is one page saying what we chose, what we rejected and why. Six months later it ends the same argument.

Your hours: the brief, the spec, the review.
The agent's hours: tickets, builds, deploys.

The harness is a preference, not the method. opencode is what I use. Any agent that can read a repository, run commands and be interrupted will do. The order of the stations is what cannot change.

4 min

This slide stops both failures at once. Expecting the agent to know what you want. Expecting yourself to review every line of code.

Harness choice is free. The stations are the method, the tool is a preference, and the order holds it together.

What goes wrong

Five ways factories stall

SymptomCause and fix
Confident work on the wrong thingNo spec, no sign-off. Gate at the spec, every time.
A ticket that never endsToo big. Slice by behaviour until it fits a day.
All checks pass, product brokenChecks written after the code. Write them red first.
Works for the agent, not for usersNo clean room. CI on every push, not on one laptop.
Nothing ever shipsMain is never green, or there is no deploy path. Ship every milestone, even a small one.

The one that hides best: an agent that says done and means "I wrote something". Ask for evidence, not the claim. Evidence is a check that failed and then passed, a green pipeline, and a running thing you can open.

5 min

Ask which of the five they recognise from their own work. Usually all five. That is the point: agents amplify an undisciplined process, they do not fix it.

The third row deserves the emphasis. It is the failure that looks like success, and the red step is the only cure.

Exercise

Your first lap

Pick something you can show a colleague in one week. That size is the point: it finishes.

  1. Write the brief. One sentence, no editing.
  2. Ask for the interview. Answer everything.
  3. Read the spec out loud. Sign it.
  4. Cut tickets. Take the smallest one that shows something.
  1. Red, then green. Ask to see the red.
  2. Push. If the project has CI, watch it go green.
  3. Close the last ticket, then merge, deploy, open it.
  4. Show one person. Then take the next ticket.

10 min, or the rest of the session

Best use of this slide: do it with the room. Ask for one idea, write the sentence together, run the interview live and stop at the spec. They will have seen the front half of the factory in twenty minutes.

A worked example to point at: the club's own MUD. One spec, milestone M1, and 28 tickets that each carry a red step and a green step.

If they do it alone afterwards: one week, one visible thing, deployed where they can open it.
